# Domain contract v1 — P0-03

Status: P1-01 implements immutable revisions; P1-02 deterministic offline planning; P1-05 local model registry/selection; P1-03 review and editorial approval; P1-04 durable RenderJob schema, snapshot/transition guards, and fail-closed enqueue/read/retry/cancel interfaces. There is no worker or renderer. The supplied skill has not passed its audit gate; no asset registry or verifiable cost-consent ledger exists, so production enqueue/retry remain unavailable. Editorial approval is not execution or paid-cost authorization. See `schemas/v1/contracts.schema.json` for record shapes and the rules below for domain invariants.

## Records and ownership

| Record | Ownership and constraints |
|---|---|
| Project | Mutable workspace metadata: id, title, idea, target, per-role model overrides, current_revision_id and approved_revision_id. A new project has both pointers null. Project targets are preferences for the next revision, never a live dependency of old revisions. |
| Storyboard | Value inside a revision: synopsis, hook, ordered scenes. Not a second independently mutable resource. |
| Scene | Revision-local value: stable id across edits, zero-based contiguous order, positive integer duration_ms, visual_direction, camera, action, narration, caption_hint and timed SFX asset IDs. Insert gets new ID; removed ID never reused. |
| Revision | Immutable from creation, including draft content. id, project_id, parent_revision_id, monotonically increasing project-local version, created_at, content and content_sha256. First parent null; later parent must belong to same project. Saving any edit creates a new record; no in-place status column in the immutable content. |
| Approval | Append-only evidence: id, project_id, revision_id, content_sha256, approved_at. No auth identity invented for single-user local mode. Server verifies hash; caller cannot assert approval by uploading a record. |
| RenderJob | Durable mutable lifecycle envelope around an immutable approved input snapshot. id, project_id, revision_id, approval_id, content_sha256, snapshot (exact RevisionContent), retry_of_job_id, created_at, status, error_code, artifact_ids, cost_consent_id. Only lifecycle/result fields may change. |

RevisionContent freezes source `idea`, target, storyboard, effective model snapshots, sorted unique asset hashes, skill_id and exact skill_version. Planner-generated revisions also include optional `planning_provenance`: source marker, exact versioned planning prompt input and SHA-256, plus exact versioned scene-generation prompt input and SHA-256. Scene prompt input is intentionally ID-independent: each draft scene has `id: null`; after insertion, `scene_id_mapping` binds its zero-based `order` to the server-assigned immutable scene UUID. Scene prompt SHA-256 covers only the prompt input, never this post-generation mapping; revision content SHA-256 covers both. Downstream scene work must join by `order` using this mapping. `deterministic_mock` identifies offline generated text; none of these inputs or hashes are evidence of remote inference or scene-code generation. Legacy manual revisions omit optional provenance, preserving their canonical content hashes. Project `idea` and `target` mirror current drafting preferences; approved content is authoritative for rendering. Asset hashes resolve to immutable local artifacts by registry, not user paths. Style/skill capabilities are checked at approval and enqueue; a name in a schema is not a claim of available support. Voice input is an approved asset; TTS/voice configuration not represented by these initial fields must be added in a new schema version before execution, never hidden in runtime defaults.

V1 scope: id-ID, 9:16, 30 fps, duration 1..60000 ms, 1..60 scenes. These are validation limits, not verified renderer capabilities. Sum of scene durations must equal target duration exactly; no rounding or truncation. SFX at_ms is scene-local and strictly less than scene duration. Duplicate scene IDs/orders, gaps and out-of-range cues fail. Narration fit requires measured audio before final render; exceeding its allocation fails rather than truncates. Frame boundaries use cumulative round(ms * fps / 1000), avoiding per-scene rounding drift; the final frame total uses the same rule.

## Immutable hashes and concurrency

Compute `content_sha256 = SHA256(UTF8(RFC8785-JCS(RevisionContent)))`; arrays retain order, asset_hashes sort lexicographically, Unicode is not normalized. Reject non-finite numbers and duplicate JSON keys before parsing. ID/version/timestamps, approval and lifecycle metadata are excluded from this content hash; target, models and prompts are included. An edit may have identical content hash but still a distinct revision ID/version: approval never transfers by hash alone. Store frozen prompt/input artifacts with hashes; hashes alone cannot reproduce remote execution. Human edits preserve planning provenance and rebuild affected scene-generation prompt snapshots before save.

The Rust domain service validates revision writes inside a SQLite transaction: expected current_revision_id matches, parent/project references are valid, revision is inserted, current pointer advances, and approved pointer clears. Review, withdrawal and approval also use serialized SQLite transactions, verify project/revision ownership and current revision, and require the exact stored content hash; stale writes return 409 stale_revision.

## Review and approval state

Review status is a separate mutable workflow record, not a revision-content mutation. New revision starts draft; draft -> in_review by explicit review request; in_review -> approved by explicit approval; review withdrawal returns in_review -> draft. New edit creates a different draft and makes the previous revision historical for navigation only. Historical approvals remain evidence; the project's approved pointer clears on edit. Approval requires the current revision in_review and a fully validated snapshot. Approval transaction appends hash-bound evidence and sets approved_revision_id = current_revision_id. Repeating approval with a new key returns existing evidence (HTTP 200); a same-key retry replays the original response. Approval proves editorial acceptance of the exact revision only; it does not authorize rendering, paid access, or skill execution.

Enqueue must name revision_id and content_sha256 and satisfy: same project; revision is current; project approved pointer names it; stored approval ID/hash/content match; supported pinned skill/model versions; valid assets and budget consent. Check and insert atomically. No current revision -> 409 approval_required; supplied non-current revision -> 409 stale_revision; current but unapproved -> 409 approval_required. Changing models, skill, target or assets at render time is forbidden: new revision/review/approval required. No historical rerender endpoint in v1.

## Job state transitions

`queued -> preparing -> voicing -> animating -> mixing -> validating -> succeeded`. SQLite guards legal transitions. Queued jobs may cancel. On every database connection, startup recovery runs in a `BEGIN IMMEDIATE` transaction: active stages become `interrupted` with `error_code='startup_interrupted'`; queued and terminal rows remain unchanged. Repeating recovery is idempotent and performs no process execution. Retry of failed/cancelled/interrupted creates a NEW job ID only after current approval/assets/cost and skill are revalidated. P1-04 fails retry closed because the audited skill and consent-evidence registries are absent. No automatic retry or new remote spend.

Succeeded requires verified nonempty artifacts and media QA; `failed`/`interrupted` require non-null error_code. P1-04 creates no succeeded jobs or artifacts and installs no worker. Job snapshots/rows persist across SQLite reopen.

## Schema vs domain validation

P1-04 QA regressions cover Store/HTTP/CLI authorization failures, asset/SFX rejection, no row creation on rejected requests, retry gating, seeded-job snapshot and transition constraints, cancellation, reopen persistence and idempotent startup recovery. No executor is installed or called by these paths; successful authorization and concurrent-success idempotency remain deferred to P1-04B pending audited skill, asset and cost evidence.

P1-03 adds the review-state and append-only approval tables/triggers in migration `0004_revision_review_approval.sql`; approval insert guards validate the current revision and stored content hash, and updates/deletes are blocked. The database enforces immutable evidence; the Store additionally serializes transitions and idempotent HTTP operations.
